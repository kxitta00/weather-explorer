# คู่มือการถามและการแก้ปัญหาเมื่อติดขัด (How to Ask & Unstuck Guide)

คู่มือนี้ออกแบบมาเพื่อให้นักศึกษาและวิศวกรซอฟต์แวร์ใช้ในการสื่อสารกับ Senior Developer หรือ AI เมื่อเจอปัญหาหรือทางตัน โดยมุ่งเน้นการสร้างกระบวนการคิดของตนเอง และไม่ตกหลุมพรางการขอโค้ดสำเร็จรูป (No Spoon-Feeding)

---

## 1. เข็มทิศเตือนสติ: เรียนรู้แบบช้าเพื่อไปได้เร็ว (Mindset: Slow is Smooth, Smooth is Fast)

- **ระวังภาพลวงตาแห่งความเข้าใจ (Illusion of Competence):**
  การรีบพิมพ์ตามหรือก๊อปปี้โค้ดเพื่อให้ได้ผลงานวิ่งเร็วๆ ไม่ใช่การเรียนรู้จริง แต่เป็นเพียงการทำหน้าที่เป็น "เครื่องพิมพ์ดีด" คุณอาจได้ชิ้นงานเสร็จเร็ว แต่จะไม่ได้ความเข้าใจ และเมื่อต้องเปิดไฟล์ว่างเปล่าขึ้นมาทำเองใหม่ จะเริ่มไม่ถูกและเกิดความหงุดหงิด
- **ความหมายของ "เดินช้าเพื่อไปได้เร็ว":**
  - การหยุดมองภาพต้นแบบแล้ววิเคราะห์กล่อง (Box Model) ด้วยตนเอง
  - การคิดหาเหตุผลว่าทำไมต้องใช้แท็กนี้ หรือใช้ CSS Property ตัวนี้
  - การร่าง State และ Data Pipeline บนกระดาษก่อนแตะคีย์บอร์ด
  กระบวนการเหล่านี้ต้องใช้พลังสมองสูงและรู้สึกช้าในช่วงแรก แต่นี่คือวิธีเดียวที่สร้าง "สัญชาตญาณวิศวกรซอฟต์แวร์" เมื่อฝึกผ่านมือตัวเองครบ ชิ้นงานต่อไปจะเร็วและแม่นยำขึ้นอย่างก้าวกระโดด
- **สัญญาณเตือนว่ากำลังเรียนผิดทาง (Red Flags):**
  - กำลังพิมพ์โค้ดโดยไม่รู้ว่าแต่ละบรรทัดทำหน้าที่อะไรในระบบ
  - พยายามแก้บั๊กด้วยการสุ่มมั่วไปเรื่อยๆ โดยไม่มีสมมติฐาน
  - รู้สึกรีบจนไม่อยากเสียเวลาอ่านเอกสารหรือวิเคราะห์กล่อง
  *หากพบสัญญาณเหล่านี้ ให้หยุดพิมพ์ทันที ถอยออกมาหนึ่งก้าว แล้วใช้กรอบการถาม 4 ระดับ*

---

## 2. เทคนิคการแกะหน้าเว็บจากภาพต้นแบบ (UI Reverse Engineering Framework)

ช่วงเริ่มต้นไม่จำเป็นต้องคิดดีไซน์เองจากศูนย์ แต่ต้องมีทักษะ "มองภาพแล้วถอดรหัสออกมาเป็นโค้ด" ให้ได้ โดยใช้ 4 ขั้นตอนต่อไปนี้:

### 2.1 หลักการมองกล่องซ้อนกล่อง (Box Hierarchy)
- ทุกอย่างบนหน้าเว็บคือ **"กล่องสี่เหลี่ยม"** ซ้อนกันอยู่เสมอ (แม้กระทั่งปุ่มทรงกลม ก็คือสี่เหลี่ยมที่ตัดขอบมน `border-radius: 50%`)
- **วิธีสแกนภาพ:**
  1. **กล่องใหญ่สุด (Outer Container):** ตีกรอบการ์ดหรือพื้นที่ทำงานหลัก (เช่น `.timer-card`)
  2. **สแกนจากบนลงล่าง (Vertical Slicing):** แบ่งหน้าจอออกเป็นแถวๆ ตามแนวดิ่ง เช่น:
     - แถวที่ 1: แถบสลับโหมด
     - แถวที่ 2: หน้าปัดตัวเลขเวลา
     - แถวที่ 3: แถบตั้งเวลา Focus / Break
     - แถวที่ 4: แถบปุ่ม Action (Start / Reset)
  3. **สแกนในแต่ละแถว (Horizontal Slicing):** ดูว่าของในแถวเรียงตัวแบบไหน:
     - เรียงแนวนอนซ้าย-ขวา -> ใช้ Flexbox แนวนอน (`flex-direction: row`)
     - เรียงแนวตั้งบน-ล่าง -> ใช้ Flexbox แนวตั้ง (`flex-direction: column`)

### 2.2 จับคู่ชิ้นส่วนกับแท็ก HTML ให้ตรงหน้าที่ (Semantic Mapping)
- **อะไรที่คลิกแล้วเกิด Action ทันที (สลับโหมด, เพิ่ม/ลด, กดเริ่ม):** ต้องใช้แท็ก `<button>` เสมอ ห้ามใช้ `<div>` ทำปุ่มมั่วซั่ว เพราะจะเสียคุณสมบัติการเข้าถึงด้วยคีย์บอร์ด (Accessibility)
- **ข้อความหัวข้อหลัก หรือตัวเลขเด่นสะดุดตา:** ใช้ `<h1>` หรือ `<h2>`
- **ข้อความกำกับ/คำอธิบายรอง (เช่น คำว่า FOCUS, BREAK TIME):** ใช้ `<p>`, `<span>`, หรือ `<label>`
- **กล่องที่ทำหน้าที่แค่จัดกลุ่ม Layout:** ใช้ `<div>`

### 2.3 แยกการใช้ Class กับ ID ให้เด็ดขาด
- **Class (`class="..."`):** ใช้สำหรับ **"การแต่งสไตล์ใน CSS"** สิ่งไหนที่มีดีไซน์คล้ายกันหรือนำกลับมาใช้ซ้ำได้ ให้ใส่ Class เดียวกัน เช่น `.stepper-btn`, `.btn-primary`
- **ID (`id="..."`):** ใช้สำหรับ **"ให้ TypeScript เข้ามาจับไปเขียน Logic"** ใส่เฉพาะองค์ประกอบที่ต้องดักจับ Event หรือต้องเปลี่ยนค่าบ่อยๆ และห้ามซ้ำกันเด็ดขาด เช่น `#timer-display`, `#start-btn`, `#focus-time-display`

### 2.4 วงจรการทำงาน 4 สเต็ป (Skeleton -> Skin -> Brain)
1. **HTML Skeleton:** พิมพ์โครงสร้างแท็กเปล่าๆ ให้ครบตามเลเยอร์ ใส่ข้อความหรือตัวเลขจำลองลงไป ไม่ต้องสนความสวยงาม หน้าตาจะดูเละเทะไม่เป็นไร ขอให้ลำดับกล่องถูกต้อง
2. **CSS Layout:** จัดตำแหน่งกล่องให้เข้าที่ด้วย Flexbox (ดึงให้อยู่ตรงกลาง, จัดระยะห่างด้วย `gap`)
3. **CSS Skin:** ลงสีพื้นหลัง, เลือกแบบอักษร, ใส่ `border-radius`, และเงา `box-shadow` ตามภาพต้นแบบ
4. **TS/DOM Brain:** สลับไปเขียน Logic ใน TypeScript และดึง ID แต่ละตัวมาผูก Event Listeners

## 3. กับดักที่ต้องเลี่ยง (Anti-Patterns)

- **ห้ามถามว่า "เขียนยังไง" หรือ "ขอโค้ดหน่อย":**
  การขอโค้ดสำเร็จรูปทำให้สมองข้ามขั้นตอนการคิดวิเคราะห์โครงสร้าง (Data Modeling, Box Model, Algorithm) ส่งผลให้เมื่อต้องเริ่มโปรเจกต์ใหม่ด้วยตนเองจะเริ่มไม่ถูก
- **ห้ามบอกแค่ "มันไม่ขึ้น" หรือ "พัง":**
  การบอกแค่อาการปลายทางโดยไม่มีข้อมูลบริบท ทำให้ผู้ตรวจไม่รู้ว่าคุณเข้าใจจุดไหนผิด และทำให้แก้ปัญหาไม่ตรงจุด
- **ห้ามแบกปัญหาทั้งหมดมาถามพร้อมกัน:**
  อย่าถาม HTML + CSS + TypeScript รวมกันในประโยคเดียว ให้แยกประเด็นและไล่แก้ไปทีละเลเยอร์

## 4. กรอบการถาม 4 ระดับ (The 4-Level Asking Framework)

เมื่อติดปัญหาหรือไม่รู้ ให้เลือกรูปแบบการถามตามระดับต่อไปนี้:

### ระดับ 1: ถามหา "ชื่อเครื่องมือหรือคลังคำศัพท์" (Tooling & Vocabularies)
*ใช้เมื่อ: รู้เป้าหมายว่าต้องการอะไร แต่ไม่รู้ว่าในภาษานี้มีแท็ก, คลาส หรือ Built-in Method อะไรที่สร้างมารองรับ*

- **ตัวอย่างคำถาม HTML:**
  - "ปุ่มสลับโหมด Focus/Break ใน HTML ปกติใช้แท็กอะไรทำ เพื่อให้ถูกต้องตามมาตรฐาน Semantic Web?"
  - "ส่วนแสดงตัวเลขเวลากลางจอ เหมาะกับการใช้แท็กประเภทไหนระหว่าง `<h1>`, `<div>`, หรือ `<p>`?"
- **ตัวอย่างคำถาม CSS:**
  - "ถ้าต้องการจัดกล่องให้อยู่ตรงกลางทั้งแนวตั้งและแนวนอนใน CSS Property พื้นฐานที่นิยมใช้คือตัวไหน?"
  - "มี Property ตัวไหนของ Flexbox ที่ใช้กำหนดระยะห่างระหว่างปุ่มโดยไม่ต้องเขียน `margin` ทีละตัว?"
- **ตัวอย่างคำถาม TypeScript / Logic:**
  - "ใน JavaScript/TypeScript มี Built-in Method ตัวไหนที่ใช้เติมเลข 0 ด้านหน้าเวลาทำรูปแบบ `05:00` บ้าง?"
  - "ฟังก์ชันที่ใช้ปัดเศษทิ้งเวลาแปลงวินาทีเป็นนาทีคือฟังก์ชันอะไร?"

### ระดับ 2: ถามเชิง "สมมติฐานและการยืนยัน" (Hypothesis & Validation - เดามาก่อน)
*ใช้เมื่อ: มีไอเดียในหัวแล้ว แต่ต้องการตรวจสอบว่าคิดถูกทางไหม หรือมีข้อเสียแฝงอะไร*

- **ตัวอย่างคำถาม:**
  - "ผมคิดว่าจะใช้ `<div>` ครอบปุ่ม `-` กับ `+` แล้วเอาตัวเลขไว้ตรงกลาง โครงสร้างแบบนี้โอเคไหม หรือมีวิธีวางกล่องที่ดีกว่านี้?"
  - "ตัวแปรจับเวลา ผมควรเก็บเป็นวินาทีรวม (Total Seconds) หรือแยกเป็นตัวแปรนาทีกับวินาที? แบบไหนเวลาเขียน Logic ลดเวลาจะควบคุมง่ายกว่า?"
  - "ผมเดาว่าควรเริ่มจับ DOM Elements มาใส่ตัวแปรก่อนเริ่มเขียนฟังก์ชันจับเวลา ลำดับความคิดแบบนี้ถูกต้องไหม?"

### ระดับ 3: ถามเจาะลึก "จุดพังจริงและกลไกการทำงาน" (Failure Point & Mental Model)
*ใช้เมื่อ: เขียนแล้วผลลัพธ์ไม่ตรง หรือเกิดพฤติกรรมที่ไม่เข้าใจ*

- **ตัวอย่างคำถาม:**
  - "ผมใส่ `display: flex` และ `justify-content: center` แล้ว แต่ทำไมกล่องยังไม่ยอมอยู่ตรงกลางจอ?"
  - "ถ้าผมกดปุ่ม Start ซ้ำๆ ทำไมตัวเลขนับถอยหลังถึงวิ่งเร็วผิดปกติ? กลไกของ `setInterval` ในระบบจริงมันทำงานยังไง?"
  - "ทำไม TypeScript ถึงแจ้งเตือนว่าตัวแปรอาจเป็น `null` ทั้งๆ ที่ใน HTML ผมก็ใส่ `id` นั้นไว้แล้ว?"

### ระดับ 4: ทางตัน 100% (The Hard Stuck Protocol)
*ใช้เมื่อ: พยายามค้นคว้า ลองเขียน และทดลองด้วยตนเองแล้วเกิน 15-20 นาที แต่ยังมองไม่เห็นทางออก*

- **คำสั่งขอคำใบ้ (Request for Hint):**
  - "เรื่อง [ระบุหัวข้อ] ผมลองคิดมา 15 นาทีแล้วตันจริงๆ รบกวนขอ Hint เชิงแนวคิด หรือ Mental Model เปรียบเทียบหน่อย"
- **คำสั่งขอตัวอย่างไวยากรณ์ (Syntax Only):**
  - "ขอตัวอย่างการเขียน [ระบุชื่อคำสั่ง เช่น `.padStart()`] แบบเดี่ยวๆ 1 บรรทัดให้ดูหน่อย ไม่ต้องเขียนโค้ดทั้งฟังก์ชันให้"
- **คำสั่งขอยอมแพ้เพื่อดูเฉลย (Surrender & Breakdown):**
  - "ข้อนี้ผมยอมแพ้ รบกวนเฉลยโค้ดส่วนนี้ให้ดู พร้อมอธิบายเหตุผลและจุดพังจริงให้ฟังอย่างละเอียด"

## 5. แบบฟอร์มการรายงานปัญหา (Problem Report Template)

เมื่อเจอ Error หรือผลลัพธ์ไม่เป็นไปตามคาด ให้ส่งข้อมูลตามโครงสร้าง 3 บรรทัดนี้เสมอ:

```text
1. สิ่งที่ต้องการให้เกิด (Expected): [อธิบายผลลัพธ์ที่คาดหวัง]
2. สิ่งที่เกิดขึ้นจริง (Actual): [อธิบายพฤติกรรมจริง หรือก๊อปปี้ Error Message มาวาง]
3. สิ่งที่ลองทำไปแล้ว (Attempt): [อธิบายว่าลองแก้ตรงไหน หรือเดาว่าเกิดจากอะไร]
```

## 6. กฎเหล็กในการฝึกฝน (Core Principles)

1. **ถามหากระบวนการคิด (Thought Process) อย่าถามหาโค้ดสำเร็จรูป (Code Output)**
2. **เอาสิ่งที่เดามาให้ตรวจ ดีกว่ามาตัวเปล่า** (การเดาผิดช่วยให้ Senior ชี้จุดที่เข้าใจคลาดเคลื่อนได้แม่นยำที่สุด)
3. **โฟกัสทีละหนึ่งเลเยอร์:** ทำโครงสร้าง HTML ให้เสร็จ -> แต่ง CSS ให้เข้าที่ -> เขียน Pure Logic ให้ผ่าน -> ค่อยต่อ DOM เข้าหากัน
